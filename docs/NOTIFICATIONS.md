# 알림(푸시) 설계

> **목적:** "오후 7시에 시작 알림, 오후 9시에 잘 끝났냐는 알림"을 어떻게 만들지 정리한 문서.
> **상태:** **2-b 통과 (2026-07-24)** — 시간 붙인 할 일을 저장하면 그 시각에 알림이 자동으로 온다
> (설치·권한·주소 발급·저장·서버 발송·시계+예약까지 한 줄로 이어짐). 지금은 **3단계(제품화)** 진행 중 —
> 실사용 버그 수정(§6-3)과 설정 화면 제품화·끄기 스위치·클릭 흐름(§6-4).
> **작성:** 2026-07-22 · **갱신:** 2026-07-27

## 0. 쉽게 말하면 (기술 배경 없이 읽는 절)

### 문제는 딱 하나다

**"앱이 꺼져 있는데 어떻게 밤 7시에 울리지?"**

폰 안의 앱은 꺼지면 아무것도 못 한다. 그러니 **그 시각에 깨어 있는 누군가**가 앱 바깥에 있어야 한다. 알림 기능은 결국 이 하나를 만드는 일이다.

### 용어 세 개

- **서버** = 항상 켜져 있는 남의 컴퓨터. 특별한 물건이 아니라 "안 꺼지는 컴퓨터"라는 역할 이름이다
- **클라우드** = 그 컴퓨터를 사서 두는 게 아니라 **빌려 쓰는 방식**. 서버가 자동차라면 클라우드는 렌터카다
- **Supabase** = 우리가 쓰는 렌터카 회사. 앱 뒷단에 필요한 것(정보를 담는 표 + 구글 로그인 + 서버에서 도는 작은 프로그램 + 정해진 시각 자동 실행)이 한 세트로 들어 있다

### 서버도 DB도 이미 있다 — 새로 만드는 게 아니다

Future Me는 **처음부터 Supabase 위에 올라가 있다.** 구글 로그인, 프로필·할 일이 다른 기기에서도 보이는 것 전부 Supabase가 하는 일이고, 설계도는 [supabase/schema.sql](../supabase/schema.sql)에 있다. 지금 표가 이미 4개다 — `futureme_profiles`, `futureme_chats`, `futureme_settings`, `futureme_goal_data`.

그래서 이번에 하는 일은 **이미 빌려 쓰는 것 위에 세 가지를 얹는 것**이 전부다.

1. **표 2개 추가** — 알림 보낼 주소록, 보낸 기록
2. **작은 프로그램 1개** — "지금 7시네? 7시 일정 있는 사람 찾아서 보내"
3. **자동 실행 켜기** — 그 프로그램이 매분 돌게

여기에 앱 쪽 작업(홈 화면에 설치 가능하게 + "알림 받기" 버튼)이 붙는다. 새로 사는 것도, 새 개념을 배우는 것도 없다.

### 우체국 비유

| 만들 것 | 쉽게 말하면 |
| --- | --- |
| PWA 껍데기 | 앱을 **홈 화면에 설치**할 수 있게 만드는 것 (아이폰은 이게 있어야 알림을 준다) |
| 서비스 워커 | 앱이 꺼져 있어도 알림을 받아 띄우는 **작은 수신기** |
| 구독 정보 | 형 폰의 **배송 주소**. "알림 받기"를 누르면 브라우저가 발급해준다 |
| Supabase | **주소록 + 시계**. 매분 "지금 7시네? 7시 일정 있는 사람?" 확인 |
| VAPID 키 | 우리 앱의 **신분증**. "이 알림은 Future Me가 보낸 게 맞다"는 증명 |

### 실제로 도는 모습 (7/23 러닝 19:00~20:00)

1. **미리 한 번:** 앱에서 "알림 받기" 누름 → 폰이 배송 주소 발급 → 서버 주소록에 저장
2. **일정 저장:** 러닝 일정이 클라우드로 올라감 (서버가 알아야 하니까)
3. **18:59:** 서버가 확인 → 아직 아님
4. **19:00:** 서버가 확인 → "이 사람 19:00 러닝 있네" → 주소로 발송
5. 🔔 *"이제 시작할 시간이야 — 러닝"* → 누르면 앱이 열림
6. **20:00:** 🔔 *"잘 끝났어? 기록해두자"*

### 사용자가 하는 건 두 가지, 그것도 한 번뿐

1. (아이폰이면) 사파리에서 **공유 → 홈 화면에 추가**
2. 앱에서 **"알림 받기"** 누르고 권한 **허용**

## 1. 무엇을 만들려는가

할 일에 시간이 붙어 있으면 (`timeStart` / `timeEnd` — 3bb8f04에서 종윤이 추가), 그 시각에 폰이 울린다.

| 시각 | 알림 | 누르면 |
| --- | --- | --- |
| 시작 시간 (예: 19:00) | "이제 시작할 시간이야 — 러닝 30분" | 앱의 홈(오늘 할 일)이 열린다 |
| 끝 시간 (예: 21:00) | "잘 끝났어? 기록해두자" | 그 할 일 체크 또는 하루 마감으로 |

**이게 왜 이 앱에 맞나:** 미래의 나가 "증거를 가진 존재"가 되려면 오늘 한 걸음이 실제로 일어나야 한다. 다만 잔소리가 되면 안 되므로 알림 문구·빈도는 §5의 원칙을 따른다.

---

## 2. 먼저 정리 — Gemma 3는 이 문제와 무관하다

찾아본 것 중에 섞여 있어서 명확히 해둔다.

- **Gemma 3 / LLM** = "무슨 말을 할지" 만드는 것
- **알림** = "정해진 시각에 사용자 기기를 깨우는" **배달** 문제

알림에 LLM은 필요 없다. 나중에 알림 문구를 미래의 나 말투로 생성하고 싶을 수는 있지만, 그건 이 기능이 돌아간 **다음** 얘기고, 서버에서 매번 LLM을 호출하면 비용·지연·실패 지점만 늘어난다. **v1은 템플릿 문구로 간다.**

## 3. 기술적으로 가능한가 — 가능하다. 방법은 사실상 하나다

웹앱을 유지하는 한 선택지는 **PWA + 웹 푸시(Web Push) + 서버 스케줄러** 하나다. 나머지는 다음 이유로 탈락:

| 방법 | 판정 | 이유 |
| --- | --- | --- |
| 앱이 열려 있을 때 `setTimeout` + `Notification` | ❌ | 탭을 닫으면 끝. 알림의 의미가 없다 |
| Notification Triggers (기기 안에서 시각 예약) | ❌ | 웹 표준으로 안 정착했다. 기대면 안 된다 |
| **PWA + 웹 푸시 + 서버 크론** | ✅ | 앱이 꺼져 있어도 온다. 아래가 이 방식이다 |
| 네이티브 앱(React Native 등) | 보류 | 알림은 제일 확실하지만 앱스토어·심사·별도 코드베이스. 지금 규모엔 과함 |

### 3-1. 도는 방식

```
[기기]                          [Supabase]                        [기기]
알림 허용 → 구독 정보 저장  →   push_subscriptions 테이블
할 일 저장 → 클라우드 동기화 →  futureme_goal_data
                                      ↓
                            pg_cron: 매분 실행
                                      ↓
                     "지금 시각 == 시작/끝 시간"인 할 일 찾기
                                      ↓
                        Edge Function: 웹 푸시 발송  →  🔔 알림
```

### 3-2. 필요한 것 (지금 없는 것)

1. **PWA 껍데기** — `manifest.json`, 서비스 워커. 지금 저장소에 둘 다 없다
2. **알림 권한 UI** — "알림 받기" 버튼 (사용자 조작에서만 권한 요청 가능)
3. **구독 저장 테이블** — 새 Supabase 테이블 `futureme_push_subscriptions`
   (`user_id`, 브라우저가 준 구독 JSON, **기기 타임존**, 켬/끔) + 발송 기록 `futureme_push_sent`
4. **스케줄러** — Supabase Edge Function + pg_cron (매분)
5. **VAPID 키 한 쌍** — 웹 푸시 신원 확인용. 한 번 만들어 환경변수로

## 4. 반드시 알아야 할 제약 3가지

### 4-1. 아이폰은 "홈 화면에 추가"해야만 알림이 온다

- 사파리 **탭으로 열어둔 상태에서는 절대 안 온다.** 홈 화면에 설치한 PWA만 가능 (iOS 16.4+, 2023년 3월부터)
- **EU 지역은 제외** (iOS 17.4+ 정책)
- → 온보딩이나 알림 설정 화면에 **"홈 화면에 추가하는 법" 안내가 필수**다. 이걸 안 하면 아이폰 사용자는 이유도 모른 채 알림을 못 받는다
- 안드로이드·PC 크롬은 설치 없이도 됨

### 4-2. 로그인이 사실상 필수가 된다

지금 할 일은 **기기 안(localStorage)에만** 있다. 서버가 모르면 시간 맞춰 쏠 수가 없다.

- 로그인 + 클라우드 동기화한 사람만 알림을 받는다
- 즉 **"알림 = 로그인 기능"** 이 된다. 로그인 안 한 사람에겐 알림 설정 화면에서 그 이유를 말해줘야 한다

### 4-3. 정확도는 ±1분

매분 도는 크론이라 19:00:00 정각이 아니라 19:00~19:01 사이에 온다. 이 용도엔 충분하다고 본다.

### 4-4. 타임존 — 서버가 풀어야 할 진짜 문제

`timeStart: "19:00"` 에는 **타임존이 없다.** 사용자 기기의 로컬 시각이다. 서버는 "지금 이 사람에게 19:00인가"를 알아야 하므로:

- 구독을 저장할 때 **기기 타임존을 같이 저장한다** (`Intl.DateTimeFormat().resolvedOptions().timeZone` → 예: `Asia/Seoul`)
- 크론은 매분 돌면서, 각 사용자의 타임존 기준 현재 `HH:mm`을 구해 할 일과 맞춰본다
- 해외에 나가면 기기 타임존이 바뀌므로, 앱을 열 때마다 타임존을 갱신해둔다

### 4-5. 중복 발송 방지

크론이 매분 돌기 때문에, 같은 할 일에 대해 두 번 쏘지 않도록 **보낸 기록이 필요하다.**

- 제안: `futureme_push_sent` 테이블에 `(user_id, todo_id, kind: 'start'|'end', fired_on: date)` 를 유니크 키로 넣고, insert가 성공할 때만 발송
- 이러면 크론이 겹쳐 돌거나 재시도해도 한 번만 간다

## 5. 알림 원칙 (PRODUCT_PRINCIPLES와의 정합)

로드맵 원칙 1이 "미래의 나가 비서·알림봇·잔소리꾼이 되는 순간 실패"다. 알림은 그 경계에 가장 가까운 기능이라 선을 미리 긋는다.

- **사용자가 시간을 적은 할 일에만** 울린다. 앱이 알아서 시간을 정해 울리지 않는다
- **하루 총량 상한**을 둔다 (예: 6개). 넘으면 안 보낸다
- **못 지킨 걸 다시 찌르지 않는다.** 재알림·"아직 안 했네?" 없음
- **끄기 쉬워야 한다.** 할 일별 / 전체 스위치
- 문구는 담담하게. 느낌표·재촉 표현 금지

## 6. 종윤과 정할 것 (5개)

1. **스케줄러를 어디에 둘까** — 제안: **Supabase**(pg_cron + Edge Function). Vercel 크론은 무료 플랜이 **하루 1회 제한**이라 이 용도로 못 쓴다
2. **FCM(Firebase)을 쓸까** — 제안: **안 쓴다.** 웹 푸시(VAPID)만으로 충분하고 FCM은 의존성만 늘어난다. FCM 자체는 무료지만 이득이 없다. (나중에 네이티브 앱으로 가면 그때 다시)
3. **로그인 필수화를 받아들일까** — 알림을 켜려면 로그인해야 한다. 이걸 온보딩에서 어떻게 안내할지
4. **아이폰 설치 안내를 어디에 둘까** — 알림 설정 화면 안? 별도 안내 화면?
5. **v1 범위** — 시작·끝 둘 다? 아니면 시작 알림만 먼저?

## 6-1. 진행 상황 (2026-07-23)

### ✅ 단계 0 통과 — 지웅님 아이폰에서 확인

홈 화면 설치 → 알림 권한 허용 → 테스트 알림이 **실제로 떴다.** 설정 화면의 진단 4줄이 모두 초록:
설치됨 / 권한 granted / 서비스 워커 / PushManager 있음.

여기서 막혔으면 서버를 만들어도 소용없었을 부분이라, 이게 관문이었다.

**같이 확인된 사실:** 테스트 알림은 **앱이 열려 있는 동안에만** 뜬다. 5초 타이머가 앱 안에서 돌기
때문에 앱을 닫으면 iOS가 코드를 재우고 타이머도 멈춘다. → 이 문서의 전제("앱이 꺼져 있어도
깨워줄 존재가 밖에 필요하다")가 실물로 확인된 셈이다.

### ✅ 1-a 통과 (2026-07-23) — 지웅님 아이폰에서 확인

**두 번째 관문 통과.** 홈 화면 앱에서 "푸시 주소 발급"을 눌렀더니 애플이 실제로 주소를 내줬다:

```
주소를 새로 발급받았어 — web.push.apple.com
https://web.push.apple.com/QFcJ0bVLr6dO0AwF8uW5pLhMOhK5wTo919ClFe4iAePZM…
```

진단 5줄 전부 초록: 설치됨 / 권한 granted / 서비스 워커 / PushManager / **푸시 주소 발급됨**.

**같이 확인된 것:** 아이폰이 주소를 내줬다는 건 **우리 VAPID 공개키를 애플이 받아들였다**는 뜻이기도
하다. 2단계에서 그 짝인 비밀키로 서명해 보내면 애플이 이 주소로 전달해준다. 즉 **배달 경로가
양쪽 다 확인됐다.**

이제 남은 건 이 주소를 서버가 알게 하는 것(1-b)과, 서버가 시계를 보다가 쏘는 것(2단계)뿐이다.

<details>
<summary>구현 내용 (1-a)</summary>

설정 화면에 **"푸시 주소 발급"** 버튼과 진단 한 줄(**푸시 주소 발급됨**)이 붙었다.
누르면 `pushManager.subscribe()` 를 실제로 시도하고, 성공하면 **어느 푸시 서버가 주소를 줬는지**
(아이폰이면 `web.push.apple.com`) 화면에 뜬다. 아직 **서버에 저장하지 않는다** — 그건 1-b다.

실패해도 이유를 구분해서 보여준다. 키를 잘못 넣은 건지 기기가 못 하는 건지 폰에서 알 수 있어야
하기 때문이다: 키 없음 / 키 형식 오류 / 권한 없음 / 설치 안 됨 / 브라우저 미지원 / 그 외(원문 표시).

"주소 버리기"로 몇 번이든 다시 시험할 수 있다.

</details>

#### VAPID 키 만들고 넣기

공개키만 앱에 들어간다. 비밀키는 **저장소에 넣지 않고** 2단계에서 Supabase 비밀값으로만 쓴다.

```
node -e "const c=require('crypto').webcrypto;const b=x=>Buffer.from(x).toString('base64url');c.subtle.generateKey({name:'ECDSA',namedCurve:'P-256'},true,['sign','verify']).then(async k=>console.log('public :',b(await c.subtle.exportKey('raw',k.publicKey)),'\nprivate:',(await c.subtle.exportKey('jwk',k.privateKey)).d))"
```

- **로컬 개발**: `.env.local` 에 `VITE_VAPID_PUBLIC_KEY=<공개키>` (`.env*` 는 git에 안 올라간다)
- **배포(폰 테스트용)**: Vercel → Settings → Environment Variables 에 같은 이름으로 공개키 추가 후 재배포.
  **이걸 안 하면 폰에서 "VAPID 공개키가 안 들어가 있어" 경고만 뜬다**
- **비밀키**: 비밀번호 관리자에 보관. 2단계 전까지 아무 데도 안 쓴다

> 키를 나중에 바꾸면 이미 발급된 주소는 못 쓴다. 그래서 발급 시 예전 키로 만든 주소가 있으면
> 자동으로 버리고 새로 받는다 (`sameApplicationServerKey`).

#### ⚠️ 실제로 겪은 사고 — Vercel 환경변수 (2026-07-23)

VAPID 공개키를 Vercel에 넣다가 **새 변수를 만드는 대신 기존 `VITE_SUPABASE_ANON_KEY` 값을
덮어썼다.** 결과: 앱 전체 로그인 불능. 증상이 "구글 로그인 눌러도 무한 로딩"이라 원인이
안 보였고, 아이폰 PWA 문제로 오해하기 딱 좋았다.

- **잡아낸 방법:** 배포본 JS를 직접 받아 확인 → `anonKey` 자리에 VAPID 키가 박혀 있었다.
  추측 대신 **빌드 결과물을 보는 게** 가장 빠르다
  ```
  curl -s https://futureme-beta.vercel.app/ | grep -oE '/assets/[^"]+\.js'
  curl -s https://futureme-beta.vercel.app/assets/<파일> | grep -oE '.{40}supabase\.co.{140}'
  ```
- **Vercel은 `Sensitive` 변수의 값을 다시 안 보여준다.** 그래서 화면만 봐선 확인이 안 된다.
  배포본을 보거나, 원본을 가진 사람에게 다시 받는 수밖에 없다
- **anon 키 원본은 Supabase 대시보드에만 있고, 그건 종윤님 계정이다** (지웅님은 접근 불가).
  1-b에서 테이블을 만들려면 어차피 필요하니 **프로젝트 멤버 초대를 받아둘 것**
- **교훈:** 환경변수는 반드시 **Add Environment Variable**로 새로 만들 것. 기존 줄을 Edit하지 말 것.
  그리고 배포 후에는 **값이 제자리에 들어갔는지 배포본으로 확인**할 것

### ⬜ 다음: 1단계를 둘로 쪼갠다

"서버 알림 지원 ●"은 **브라우저에 PushManager가 있다**는 뜻일 뿐, **실제로 구독(배송 주소)이
발급되는지**는 아직 확인 안 됐다. 아이폰에서 여기서 막히면 또 멈춘다. 그래서:

| | 내용 | 확인 방법 |
| --- | --- | --- |
| ~~**1-a**~~ | `pushManager.subscribe()` 로 **주소 발급만** 시도하고 성공/실패를 화면에 표시 | ✅ **통과** — `web.push.apple.com` 확인 |
| 1-b | 성공하면 Supabase 테이블(`futureme_push_subscriptions`) 만들고 저장 | — |
| 2 | 서버 스케줄러 (pg_cron + Edge Function) | 앱 꺼둔 채로 알림 오는지 |

1-a에 VAPID 키 한 쌍이 필요하다(공개키만 앱에 들어간다). 30분이면 만들어 확인할 수 있다.

### 배포 흐름 (2026-07-23부터)

저장소가 **public**으로 바뀌어서 Vercel의 커밋 작성자 검사가 사라졌다. 이제 지웅님이 PR을
만들고 **직접 병합**할 수 있고, 병합되면 Vercel이 자동 배포한다. 종윤님을 거칠 필요 없다.

## 6-2. ✅✅✅ 2-b 통과 = 목표 달성 (2026-07-24)

**앱에서 시간 붙인 할 일을 저장하면, 그 시각에 알림이 자동으로 온다.** 이 문서 맨 위의 목적이
실제로 작동한다.

실물 확인: 맥북 앱에서 "테스트 16:15~16:20" 저장 →
- 앱이 예약표(`futureme_reminders`)에 시작/끝 2줄 자동 등록 (배선 작동)
- pg_cron 매분 → **16:15 시작 알림, 16:20 끝 알림**이 아이폰 잠금화면에 도착
- `futureme_push_sent` 확인: start·end 각각 **2대**(web.push.apple.com + fcm.googleapis.com)
  → 다기기 발송까지 확인

전체 사슬: 도장(1-a) → 주소록(1-b) → 발송(2-a) → 시계+예약(2-b)이 한 줄로 이어졌다.

**설계 요점(왜 이렇게):**
- "오늘 이 시각의 할 일 찾기"는 복잡한 트리 탐색이라 서버에서 다시 짜지 않고, **앱이 검증된
  로직으로 예약표를 평평하게 펼쳐** 두고 크론은 "지금 == 예약 시각?"만 본다
  (`src/lib/notifyReminders.ts` → `reminderSync.ts` → `futureme_reminders`).
- 수동 SQL로 예약을 넣는 테스트는 **취약하다**: 앱이 동기화하면 예약표를 통째로 갈아끼워
  수동 예약이 지워진다. **진짜 시간 붙은 할 일**로 만든 예약만 살아남는다(재동기화 때
  똑같이 다시 만들어지므로). 시험은 반드시 실제 할 일로 할 것.

**겪은 버그 2개(수정함):**
- **다기기 한 대만 발송** — `push_sent` 중복방지 키에 endpoint가 빠져, 첫 기기가 기록을
  남기면 같은 사용자의 둘째 기기가 충돌해 건너뛰어졌다. 키에 endpoint 추가로 해결
  (`fix/push-multi-device`). ⚠️ 함수는 대시보드 재배포됨, **브랜치는 main 미머지 — 머지 필요.**
- **작은 아이폰에서 시간 저장 버튼이 화면 밖으로 잘림** — 시트 max-height를 dvh로,
  액션바를 sticky로 (`fix/task-time-sheet-cutoff`). ⚠️ **미머지·미배포 — 아이폰 시간 저장
  아직 막힘. 머지·배포 필요.**

## 6-3. 실사용 버그 2개 수정 (2026-07-27) — `fix/notify-body-and-sync`, main 머지됨(PR #12)

폰 2대(서로 다른 계정)로 실사용하며 나온 버그.

- **알림 본문 빈칸**(제목만 뜨고 본문이 안 보임): 아이폰은 `title`은 확실히 띄우지만,
  서버 payload가 `event.data`로 안 오면 `body`가 통째로 사라진다. 그런데 그동안 `title`이
  `'Future Me'`(서비스 워커 기본값)라 **payload가 왔는지조차 구분이 안 됐다.** 실제 문구를
  `body`→`title`로 옮겨(§push-tick), 그 경우에도 내용이 보이고 도달 여부 진단도 되게 했다.
  서비스 워커도 `json()`→`JSON.parse(text())` 방어 파싱 + payload 미도달 시 빈칸 대신
  `"알림 내용을 불러오지 못했어"` 표시.
- **기기 간 동기화 지연**(한 기기 저장이 다른 기기에 반영 안 됨): 동기화가 로그인 시 1회뿐이라
  이미 열려 있는 기기가 못 당겨왔다. `focus`/`visibilitychange`에 재동기화 리스너 추가
  (`AuthContext`, 기존 5분 스로틀 유지).

## 6-4. 3단계 — 알림 제품화 (2026-07-27~)

시험용으로 만든 설정 화면·흐름을 **제품 품질로** 다듬는 단계. 하루 상한(§5)은 **뺐다** —
"계속 동기부여받고 싶은 사용자에겐 상한이 오히려 방해"라는 판단. 필요하면 나중에 옵트인으로.

| | 내용 | 상태 |
| --- | --- | --- |
| **설정 화면 제품화** | 진단 6줄·"푸시 주소 발급"·raw endpoint·시험 문구를 접고, 일반 사용자는 **"알림 켜기" 한 번**(권한→발급→저장 자동)만 보게. 진단·테스트는 "문제가 있나요?" 접이식 안으로 | ✅ 브랜치 `feat/notify-productize` |
| **끄기 스위치 — 기기별** | 구독 `enabled`를 토글하는 "이 기기 알림 켜기/끄기" (`setPushEnabled`). 끄면 크론이 그 기기를 건너뛴다 | ✅ 같은 브랜치 |
| **알림 클릭 흐름** | 콜드 오픈은 기본 탭이 이미 '오늘 홈'이라 충족. 이미 떠 있는 창은 서비스 워커가 `futureme-open` 메시지 → 앱이 홈 탭으로 전환 | ✅ 같은 브랜치 |
| **끄기 스위치 — 할 일별** | 할 일마다 알림 on/off. 아이템 모델(`goalPlan.PlanCheckItem`/`MiscTodoItem`)에 `notifyOff` 추가, `deriveReminders`가 건너뜀, 시간 시트에 "알림: 받기/안 받기" 세그먼트 | ✅ 브랜치 `feat/notify-per-todo-toggle` (프리뷰에서 저장·재오픈 왕복 확인) |
| 끝 알림 → 하루 마감 | 지금은 시작·끝 모두 홈으로. 끝 알림은 하루 마감으로 다듬기 | ⬜ 나중 |

## 6-5. 동기화 견고성 (2026-07-27~)

알림은 서버의 예약표(`futureme_reminders`)에 기대는데, 그 예약표는 앱이 목표 데이터를 올릴 때
같이 만든다. 그래서 목표 데이터 동기화가 튼튼하지 않으면 **알림도 조용히 사라진다.**

| | 내용 | 상태 |
| --- | --- | --- |
| **올리기 전 병합 (덮어쓰기 경쟁 수정)** | 디바운스 푸시가 원격을 안 보고 로컬로 덮어써서, 오래된 기기가 저장하면 다른 기기가 추가한 할 일·예약이 지워졌다. 이제 **올리기 전 원격을 fetch→병합→로컬 반영 후 push** | ✅ `feat/notify-sync-robust`(PR #15) |
| **↳ 회귀 수정: 방금 넣은 시간이 사라짐** | 위 병합을 번들 단위 타임스탬프로 했더니 시계 어긋남에 폰 편집이 덮어써짐. 1차로 additive(`absorbRemoteOnly`, 같은 id 무조건 로컬)로 막음 | ✅ PR #16 → **아래 항목별 병합으로 대체됨** |
| **↳↳ 항목별 최신 우선 (체크·시간 편집이 기기 간 반영 안 되던 문제)** | additive는 "같은 id 무조건 로컬"이라, 이번엔 **다른 기기의 체크·시간 편집을 이 기기가 덮어써서** 맥→폰 편집이 반영 안 됐다(추가만 됨). 근본 원인은 **할 일에 항목별 수정 시각이 없어** 어느 편집이 최신인지 못 정하는 것. `MiscTodoItem`에 `updatedAt` 추가 + 모든 수정 함수가 갱신 + `mergeMiscTodos`를 **항목별 최신 우선**으로. 이러면 추가·체크·시간이 방향 무관하게 반영되고 "시간 사라짐" 회귀도 근본적으로 막힌다. 푸시 경로도 additive 대신 이 병합을 씀 | ✅ 브랜치 `feat/notify-realtime-sync` (같은 브랜치) |
| **실시간성 (양방향 즉시 반영)** | 로그인·포커스 때만 당기던 걸, **Supabase Realtime 구독**으로 다른 기기 변경을 즉시 받게. 앱을 켜둔 채 가만히 둬도 반영. 에코 방지는 **내용 기반**(시계값 무관 — 회귀 재발 방지). 백그라운드로 소켓이 잠들 수 있어 **돌아올 때 캐치업 당김**(`pullRemoteGoalDataOnce`, 스로틀 없음)을 함께 둠 → Realtime이 꺼져 있어도 "열면 반영"으로 우아하게 강등 | ✅ main 머지(PR #17). Supabase publication에 테이블 추가함. 폰↔맥 실검증: 체크·시간 편집 3초 내 양방향 반영 |
| **삭제 전파 (지운 게 되살아나던 문제)** | 일상 할 일을 지우면 배열에서 그냥 빠져서 "지웠다"는 사실이 동기화로 안 갔다 → 다른 기기에 남아 있으면 부활. **툼스톤**(`MiscTodoItem.deletedAt`)으로 바꿔 삭제도 동기화. 병합은 삭제 시각 vs 편집 시각을 비교(늦은 쪽이 이김 → 삭제 후 편집하면 부활). 화면·예약·집계에서 걸러내고, 60일 지난 툼스톤은 정리 | ✅ 브랜치 `feat/misc-todo-tombstones` (테스트 포함) |
| **↳ 남은 것: 목표 트리 내부 항목** | 일상 할 일은 항목별 병합이 됐지만, **목표 안의 날짜별 할 일**은 아직 목표(플랜) 단위로 병합돼, 같은 목표 안 여러 편집이 통째 병합에 묻힐 수 있음 | ⬜ 다음 |

## 7. 비용과 일정

### 비용: 0원

| 항목 | 요금 | 근거 |
| --- | --- | --- |
| Supabase | 무료 | Edge Function 월 50만 회 무료. 매분 크론 = 월 43,200회 |
| 웹 푸시 발송 | 무료 | 브라우저 표준. 발송 자체에 요금 없음 |
| Vercel | 무료 | 정적 호스팅 그대로 (크론은 안 씀) |
| FCM (쓸 경우) | 무료 | 발송 무제한 무료. 다만 §6-2대로 안 쓰는 걸 제안 |

주의: Supabase 무료 프로젝트는 **7일간 요청이 없으면 일시정지**되는데, 매분 크론이 도니까 해당 없음.

### 일정: 약 3일

| 단계 | 내용 | 시간 |
| --- | --- | --- |
| 0 | **테스트 관문** — PWA 껍데기 + 알림 권한 + "테스트 알림 보내기" 버튼 | 0.5일 |
| 1 | 구독 저장 (테이블 + 저장/해지) | 0.5일 |
| 2 | 스케줄러 (Edge Function + pg_cron + 중복 발송 방지) | 1일 |
| 3 | 알림 눌렀을 때 흐름, 끄기 스위치, 하루 상한 | 1일 |

**단계 0을 먼저 하고 멈추자.** 지웅 폰(아이폰)에서 실제로 알림이 뜨는지 확인하는 게 관문이다. 여기서 막히면(설치 안내, 권한, 지역 제한) 나머지는 지어봐야 의미가 없다. 반나절이면 답이 나온다.
